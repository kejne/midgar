# Midgar dispatch helper contract

`commands/midgar/factory dispatch ISSUE --rig RIG` accepts a GitHub issue URL or `OWNER/REPO#NUMBER` and a registered non-HQ Gas City rig. The helper reads issue state with `gh`, resolves the rig with `gc rig list --json`, and verifies the rig's actual GitHub `origin` with `git`. It rejects the dispatch unless the issue has the `ready-for-agent` label and both repositories match. No work is released by this helper.

Successful dispatch writes one JSON run record to `.gc/specs/.runs/ISSUE-KEY.json` and prints that record as one JSON object. `ISSUE-KEY` is the SHA-256 digest of the normalized JSON tuple `[lowercase owner, lowercase repository, issue number]`; the same traversal-safe key names the active-run record and per-issue lock, avoiding delimiter collisions. Its stable fields are `run_id`, `issue`, `repository`, `rig`, `stage`, `progress`, and `snapshot`. Run data and snapshots are local operational artifacts and are ignored by Git.

The first dispatch captures issue title, body, URL, and comments as `.gc/specs/RIG/NUMBER/snapshot.json`. Later dispatches resolve the existing run without rewriting that snapshot, and a run requested on another rig is rejected. `--replace` is the explicit operator boundary for archiving the existing run and creating a replacement; it preserves the active snapshot, including a reconciled revision. When replacing onto another rig, it copies the exact active snapshot bytes into that rig's snapshot artifacts without overwriting an existing artifact (using an unused immutable revision path when needed). It never refreshes the replacement snapshot from changed issue content. `--reconcile` instead explicitly adopts current source issue data into a new immutable `snapshot.revision-N.json` and updates the active run's snapshot pointer without replacing the run or deleting its prior snapshot. The two flags cannot be combined. Concurrent calls serialize on a per-source-issue lock and resolve to the same active run. Historical run records are retained under `.gc/specs/.runs/archive/`.

`record_stage(ISSUE, STAGE, PROGRESS, DIAGNOSTICS=None)` is the downstream factory-level write contract for updating a run's stage, merging progress references, and appending a diagnostic record. It shares dispatch's per-issue lock and atomically replaces the run JSON, so concurrent dispatch and stage writes are serialized. `stage` describes factory-level progress only; it does not duplicate or override Beads task-status authority. Paused and failed stages and their diagnostics are retained in the active run record.

Run records, archived run records, diagnostics, and snapshots are retained indefinitely by this foundation. There is no automatic cleanup or delete path. Removal requires an explicit safe operator cleanup decision; PR lifecycle and cleanup automation remain out of scope.

Issue #6's immutable spec snapshots store requirements only: the issue title, body, URL, and comments. Run stage and progress references are stored separately in run records; neither execution plans nor run requirements are stored in the snapshot or run record. This helper does not materialize an execution plan. Any future versioned plan artifacts must be separate from the requirements snapshot and reference it. Issue #8 owns defining and materializing those plan artifacts.

This helper also does not create Beads tasks, provision workspaces, run agents, publish a PR, or provide a review/cleanup lifecycle. Those are outside issue #6's deterministic dispatch/run/snapshot foundation.
