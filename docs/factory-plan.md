# Execution plans

`commands/midgar/plan.py` owns the public `validate_plan(plan, acceptance_ids)` and `materialize_plan(issue, plan, acceptance_ids, specs_root, command)` seams. The CLI is `commands/midgar/plan validate PLAN.json ACCEPTANCE.json` or `commands/midgar/plan materialize ISSUE PLAN.json ACCEPTANCE.json`. The acceptance file is a JSON array of stable criterion IDs transcribed from the active spec snapshot; this helper does not reinterpret or modify snapshot requirements.

A plan identifies `run_id`, has a positive integer `revision`, references the exact active snapshot path, and has a non-empty `tasks` list. Each task has a unique portable `id`, `title`, independently verifiable `behavior`, non-empty `acceptance` list of criterion IDs, `owns` criterion IDs, and `depends_on` task IDs. Every snapshot criterion is owned and verified by a task. A criterion claimed by multiple tasks requires `integration_owner: {"CRITERION-ID": "task-id"}` selecting one of those tasks. Plan validation rejects malformed or duplicate identities, unknown/missing references, uncovered or unknown criteria, unresolved shared ownership, self-edges, and cycles before any Beads/convoy command runs.

Revisions are separate from `snapshot.json` and stored as `RIG/ISSUE/plans/revision-N.json`. Reusing the same revision with different content is rejected. Materialization reads the active run and its immutable snapshot while holding the same per-issue lock used by dispatch; the plan's `run_id` must match, so a replaced run cannot reuse a stale plan. A run-level manifest records task fingerprints and the exact accepted criterion-ID set before remote writes; all later revisions must retain that set. Changing/removing an existing task or changing acceptance IDs fails for explicit reconciliation. Revisions may add new task identities without rewriting prior work.

## Materialization and resume contract

Every native read/write is routed through `gc --rig RUN-RIG bd ...` or `gc --rig RUN-RIG convoy ...`; no bare `bd` call depends on the caller's Midgar checkout. The selected run rig is validated from the active run record while the issue lock is held. Each implementation task uses `external_ref=midgar:RUN-ID:task:TASK-ID` and metadata containing source issue, run, and task IDs. Resume resolves by external reference and verifies the retrieved Beads record's ID, external reference, and metadata before trusting it. If creation succeeded remotely but its response was lost, the exact task is found and verified on retry.

Dependencies use `bd dep list TASK --json` to confirm the exact `blocks` edge before adding it with `bd dep add TASK-BEAD PREREQUISITE-BEAD`, and confirm it afterward. This read-after-write reconciliation handles an interruption after remote success but before the local ledger update.

Exactly one owned convoy per run uses title `Midgar RUN-ID ISSUE implementation tasks`. Resume searches `gc --rig RUN-RIG bd list --all --type convoy --title TITLE --json` (including closed beads), then checks `gc convoy status ID --json` for exact ID/title and `owned: true`. A created convoy is verified the same way. Its ID and `convoy_owner=midgar:RUN-ID` are recorded in the run; mismatches fail closed. The convoy status children are authoritative for membership: resume rejects foreign/source/control members, adds only missing implementation beads via `gc convoy add CONVOY-ID BEAD-ID --json`, then re-reads status. A lost add response is therefore reconciled without duplicate membership. The native CLI has `create`, `list`, `status`, and `add` (not a `populate` subcommand); add creates a `tracks` relationship and does not change task parentage.

Beads remains live task-status authority. `.gc/specs/.runs/RUN-ID.plan-state.json` is only an external-operation recovery ledger. Before external writes, run progress marks `plan_ready: false`; it becomes true only after all task identities, dependency edges, and exact convoy membership are verified. A failed or interrupted materialization remains not-ready. No source issue, parent planning bead, or drain/control bead is placed in the implementation convoy.

## Parent-graph handoff

`materialize_plan` returns `{run_id, plan, revision, convoy_id, tasks, ready}`. The parent graph must gate release on `ready is true` and the active run's `progress.plan_ready is true`; convoy ID presence alone is not a success signal. Once ready, the parent drain/control bead stores the returned ID in native metadata `gc.input_convoy_id`, which the installed Midgar claim helper uses to scope drain claims. Do not add the source issue or parent bead as convoy members: the convoy tracks only implementation tasks. The materializer does not trigger a drain or reproduce Gas City's scheduler.

## Installed CLI contract checked

Validated against installed Gas City `gc 1.5.0` and Beads `bd 1.3.1`. `gc --rig RIG bd ...` selects the target rig's store (a nonexistent rig is rejected); `gc convoy status` reports the convoy's ID, title, status, and owned bit. `gc convoy create --owned --json` returns `convoy_id` and `title`; `gc convoy add` reports membership. `bd list --all --type convoy --title ... --json` includes closed convoys, and `bd dep list --json` returns `issue_id`, `depends_on_id`, and `type`. `bd create` supports `--external-ref`, `--metadata`, `--acceptance`, and `--json`; `bd list` supports `--all --external-ref REF --json`; `bd dep add` accepts dependent and prerequisite IDs positionally and creates a `blocks` edge by default. This is a CLI contract check only; no running city or Beads database is required for the normal tests.
